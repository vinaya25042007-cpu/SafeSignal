Disaster Resilient Technology

SafeSignal

Wireless Emergency Communication System

An off-grid, low-latency, peer-to-peer radio messaging network enabling physical-button disaster triage without cell towers, Wi-Fi routers, or internet.

📻 Protocol: ESP-NOW (2.4 GHz) ⚡ Hardware: ESP32-WROOM-32 ⏱️ Latency: < 2 ms
The Motivation

The Problem: Communication Blackouts

🌪️

Infrastructure Collapse

Earthquakes, floods, and storms destroy base transceiver stations (BTS), cut fiber lines, and shut down electrical power grids.

📵

Smartphone Dependency

Traditional emergency systems rely entirely on smartphones, cellular SIMs, or internet connectivity—rendering them useless during disasters.

⏳

Lost "Golden Hour"

Search & rescue teams waste critical hours wandering blind because there is no localized triage signaling who is safe versus who needs immediate medical rescue.

The Solution

SafeSignal: Off-Grid Wireless Triage

💡 What is SafeSignal?

A portable, two-node wireless communication system operating over ESP-NOW radio protocol. It converts physical button presses into encrypted wireless status packets in real time.

  • Zero dependencies: No Router, No Internet, No SIM
  • Tactile 3-button human interface (accessible to children & injured)
  • Immediate visual & acoustic status triage

🎯 Core Engineering Objectives

Off-Grid Autonomy: 100% peer-to-peer radio link
Sub-Second Triage: Immediate packet arrival (<2ms)
Fail-Safe Delivery: 3-stage hardware retry & link acknowledgment

Structured Message Payload

Transmitter sends a strongly typed binary C-struct containing message sequence numbers, emergency enum codes, and timestamps:

typedef struct struct_message {
  uint32_t messageId;       // Sequence ID
  EmergencyStatus status;   // 1=SAFE, 2=HELP, 3=MED
  char statusText[24];      // Status Label
  uint32_t timestamp;       // Millis timestamp
} struct_message;

Operational Logic

Status Output Matrix & Triage Rules

🟢 SAFE

Code: 1

Green LED: ON

Yellow & Red: OFF

Buzzer: SILENT

Indicates household is secure. Responders bypass to next zone.

🟡 NEED HELP

Code: 2

Yellow LED: ON

Green & Red: OFF

Buzzer: SILENT

Non-critical aid required (clean water, rations, minor repairs).

🔴 MEDICAL ALERT

Code: 3

Red LED: ON

Green & Yellow: OFF

Buzzer: PULSING ALARM

Critical life threat. Search & rescue dispatched immediately!

*Latching Mechanism: Sending a new status immediately switches outputs and mutes the siren.*

Firmware Engineering

Firmware Reliability & Fail-Safes

🛡️ Software Debounce

Mechanical pushbuttons chatter upon contact. We implemented a 50ms stable-state non-blocking time window to eliminate false multiple triggers.

🔁 3-Stage Retry Logic

If link-layer ACK fails (e.g. RF interference), the transmitter executes up to 3 automatic retries with 150ms backoff before flagging a delivery alert.

🔄 Dual-Core Compatibility

Utilizes preprocessor conditional compilation to seamlessly support both Arduino ESP32 Core 2.x and Core 3.x/4.x callback type signatures.

Future Scope

Project Roadmap (Phases 4 – 7)

📡 Phase 4: LoRa Gateway (5–10 km Range)

Replacing/bridging ESP-NOW with SX1278 / SX1262 LoRa modules over SPI to scale communication across vast mountain, rural, or maritime disaster terrain.

🗄️ Phase 5: FastAPI + SQLite Gateway

Central receiver node streams JSON payloads over USB/Serial to a lightweight FastAPI server that logs emergency timestamps, RSSI, and responder acknowledgment.

💻 Phase 6: React Dispatcher Dashboard

A web-based incident dashboard visualizing incoming emergency markers, alert feeds, audio alarms, and one-click incident clearance.

⚖️ Phase 7: Priority Algorithm vs. FCFS

Benchmarking First-Come-First-Served (FCFS) against Rule-Based Priority Ranking (Medical > Help > Safe) to prove reduced critical dispatch latency during alert storms.
